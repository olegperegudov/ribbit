## Design Specificity Verdict

**LLM assessment.** The log screen is genuinely authored for this product; the settings panel is not. The signature row (timestamp, wrapped text, a 6px provenance dot with `groq | llama-3.3-70b` underneath, the whole row copying with a green wash), the day separator whose gradient rules fade out from a lowercase `mo, jul 13th`, the 6×32px meter standing beside the pixel frog, and the fuchsia selection that turns a mangled word into a permanent rule — none of that lifts into another app without carrying Ribbit's premise with it. Then you open the gear and the authorship stops: label-left/control-right rows, a stock 36×20 iOS toggle, native selects, provider cards laid out url/model/key exactly as any dark developer tool would lay them out. Ribbit has one great screen and one generic one, and the generic one is where all the hard decisions live.

## Overall Impression

Ribbit is a one-screen product with a second screen bolted on. The log is the work of someone who thought hard about a glance: a row that is simultaneously a record, a copy button, and a provenance trail, in a card small enough to read in a second. The settings panel is where every hard decision was deferred — eleven undifferentiated rows, the rarest configuration in the product (provider url/model/key) given permanent full height, and the most valuable data in the product (a vocabulary built by hand over months) one stray 15px click from deletion with no undo.

The single biggest opportunity is not visual. It is that a failed dictation — the one moment where the user has lost something — is announced in the success colour, truncated mid-sentence, for five seconds, in a window that is closed.

## What's Working

**The log entry as both record and control surface.** One row carries time, text, and provenance, and the row *is* the copy button — success is the row changing colour, not a toast appearing elsewhere. In a 400×440 card every pixel of chrome is stolen from content, and this design spends zero on confirmation UI while still confirming. The provenance line makes an invisible pipeline decision auditable per line.

**The teach-in-place vocabulary loop.** Select a mangled word, the fuchsia highlight survives the focus moving to the popup, an existing target is offered, Enter commits, and the already-visible log is rewritten. The user sees the correction applied to the past, not merely promised for the future. Most products would save the rule and leave the screen stale; that retroactive rescan is the emotional payoff of the whole feature.

**The recessed group with the 2px green left edge.** The speech stack and the LLM block take a darker fill, an inset shadow, an asymmetric radius, and drop their per-row dividers. It answers "which rows belong to this toggle" with tone instead of an indent or a box — an indent would break the label column, a box would cost 2px of width on each side in a card that has none to spare.

## Priority Issues

**[P0] A failed dictation is announced in the success colour, truncated, for five seconds, in a window that is closed.**
- *Why it matters:* this is the product's only genuinely high-stakes failure — macOS revoked Accessibility, so nothing was typed anywhere. PRODUCT.md names exactly this case. Today the message is green (the app's own success colour, breaking DESIGN.md's One Light Rule), cut off after ~44 characters in a ~241px nowrap field, and lowercased — so `System Settings → Privacy & Security → Accessibility`, the one string the user must follow literally in a system dialog, arrives mangled and headless.
- *Fix:* an `.error` state on `#status-detail` (red, wrapping); stop lowercasing a message that is content, not the product's voice; write failures into the log as a `.log-entry.failed` row with a red dot and the full text; and swap the tray icon on failure using the same path `announce_update()` already uses, clearing on the next success.
- *Suggested command:* `/impeccable clarify`, then `/impeccable harden`

**[P1] Two destructive controls, identical treatment, different blast radius, no undo.**
- *Why it matters:* `.vocab-alias-x` removes one alias; `.vocab-row-x` removes the term and every alias under it. Both are faint grey turning red on hover, a few pixels apart in the same row, both commit immediately, and neither re-renders the log — so nothing on screen signals what was lost. The vocabulary is the product's second differentiator and the thing the user built by hand over months. `.provider-del` deletes a provider and its saved key the same way.
- *Fix:* give the row-level × its own 24px gutter away from the alias chips, and put it behind the two-step the codebase already has (`showMergePopup`): first click turns × into `remove?`, second commits, 3s timeout reverts.
- *Suggested command:* `/impeccable harden`

**[P1] The settings panel is an eleven-row flat list whose two largest blocks are permanently expanded.**
- *Why it matters:* each provider card is ~113px, and the speech stack renders one per provider — with five providers that stack alone is ~600px inside a ~370px scroll region, pushing hotkey, vocabulary and history off-screen behind configuration a user touches once a year. This single decision causes four of the cognitive-load failures at once. Every `.setting-label` is the same 0.75rem grey, so `speech providers` (a section head introducing ~230px of content) is typographically identical to `sound` (a two-option select).
- *Fix:* collapse a provider card to a one-line summary (`Groq · PRIMARY · api.groq.com`, chevron right) that expands on click, and group the remaining rows under three micro-headers reusing the day-separator treatment: *input* (hotkey, sound, languages), *text* (vocabulary, edit transcription), *data* (history, debug log, version).
- *Suggested command:* `/impeccable layout`, then `/impeccable distill`

**[P1] The log is mouse-only, and the ramp it is drawn in fails contrast.**
- *Why it matters:* copying a line is the whole reason the window opens, and `.log-entry` has no tabindex, no role and no keydown — there is no keyboard route to the product's primary in-window action, and no ⌘F. Its only affordance hint is a native `title`, which the stylesheet itself documents as silent on WKWebView. Meanwhile `#4b5563` (timestamps, `?` hints, edit links, empty states) measures 2.47:1 and `#6b7280` (provider labels, hotkey display, panel buttons) 3.42–3.86:1 — both fail AA, and the `?` icon whose entire job is to be found is the worst offender at 13×13px.
- *Fix:* make the log entry a real button (or tabindex + role + Enter/Space) with a focus ring scoped to the log — the global `outline: none` is scoped to header buttons and dots, so it will not collide. Move `click to copy` onto the `data-hint` system. Lift `.log-time` to `#6b7280`, `.hint-icon` to `#9ca3af`, and raise the 8.8–9.9px labels to the 11px floor.
- *Suggested command:* `/impeccable audit`, then `/impeccable typeset`

**[P2] One long dictation eats the whole card.**
- *Why it matters:* a one-minute dictation (~900 characters) renders ~18 lines ≈ 260px inside a ~370px log region. The window is meant to be a glance; one long entry turns it into a scroll and buries the four lines the user came back for. Every existing screenshot shows one- and two-line entries, so this composition has never been checked against its own worst case.
- *Fix:* clamp the text to 4 lines with a faint `+14 lines` control in the meta row that expands in place. Copy reads `textContent`, which stays complete under a clamp.
- *Suggested command:* `/impeccable adapt`

## Persona Red Flags

**Alex (power user)** — the window is a mouse-only surface. The log entry is not focusable, so the primary action has no keyboard path. There is no ⌘F handler anywhere. Escape is handled in the search field, the vocab popup and the hotkey capture, but not in settings, vocabulary or debug — once he is in settings the keyboard cannot get him out. Provider priority is changed only by clicking the ↑/↓ mini-buttons, whose meaning lives in the native `title` this codebase knows WKWebView will not render.

**Sam (accessibility-dependent)** — the faint ramp carries load-bearing content (2.19–3.86:1, listed above), several of those elements are interactive and 8.8–10px. The `.log-llm-dot` is a focusable span with no text, no `aria-label` and no title — a screen reader announces nothing — and it encodes edited/unedited in colour alone. Fifteen-plus inputs have no programmatic label (no `for`, no `aria-labelledby`, no `aria-label`): search, vocab add/search, sound, history, language, every provider url/model/key field, both fallback knobs, the API key field. Six controls have a single symbol glyph (`×`, `+`) as their entire accessible name. `#log-entries` has no role and no `aria-live`, so a transcription arriving while the window is open is announced to nothing.

**The bilingual developer (PRODUCT.md's actual user)** — his own screenshot contradicts the design system: in `docs/screenshots/log.png` Latin runs render monospace while Cyrillic runs fall back to a proportional face inside the same sentence. There is no `@font-face` and no bundled font file, so the app relies on JetBrains Mono being installed and the fallback resolves per glyph. DESIGN.md's claim that mixed Cyrillic/Latin keeps its rhythm is falsified by the app's own evidence. Second: the vocabulary list sorts Latin keys before Cyrillic unconditionally, so at 50 entries every Russian term he taught sits below the fold. Third: nothing states whether selecting two languages means "either one" or "both inside one sentence" — his actual case — and the `?` hint answers a different question.

## Minor Observations

- The zero-entry log has no empty state at all; a fresh install with a saved key shows a blank region. The vocabulary panel handles the identical case with real copy.
- Search with no hits produces the same blankness — every entry and separator is hidden and nothing is rendered in their place.
- On first run the setup block sits after the log region in the DOM, and the log region is `flex: 1`, so the three setup steps are pinned to the bottom of an empty card rather than being the card. (Code-derived; not visually verified.)
- `Search...` in the log header, `search...` in the vocabulary panel. The Lowercase Rule loses by one character.
- In `docs/screenshots/vocab.png` the vocab popup covers the second line of the very entry being taught.
- The merge prompt auto-dismisses after 5s and silently re-renders as if "no" were chosen — a decision that resolves itself by timeout. Its copy also carries a stray space-colon.
- `⚡` in the fallback banner and `⚠` in the LLM error are the only two symbol glyphs in a system that otherwise expresses status with a 6px dot and a bordered tag.
- The `←` in the vocab add row reads right-to-left against a left-to-right form: the user fills the left field with the answer before naming the problem.
- The settings panel has no panel header — no title, no × — while vocabulary and debug both do, and both of their × buttons return to the log rather than to settings, where the user came from.
- `docs/screenshots/*.png` still show the minimize and close buttons that no longer exist in the markup. Treat them as evidence of composition, not of current chrome.
- Spacing is monotonous by measurement: ~4px accounts for ~88% of all gaps. Grouping is carried almost entirely by hairlines and tone, with rhythm doing none of the work.

## Questions to Consider

1. The menu-bar icon already changes colour to announce an available update. Why does a pending download earn a persistent signal all day, while a dictation that never reached the app earns five green seconds in a hidden window? What does Ribbit become if the tray icon is the status surface and the window is only the record?
2. If the log is the product's memory and the memory is meant to be honest about failures, why is there no failed row in it? The words *were* transcribed — only the insert failed. What if a failure were an entry: timestamp, the text you actually said, a red dot, and one click to retry the insert?
3. Settings are visited rarely and deliberately — so why is the panel optimised for scanning rather than for arriving? What if the gear landed on the four things people come back for (hotkey, vocabulary, edit on/off, history), and everything provider-shaped lived one level deeper, exactly as vocabulary and debug already do?
4. Teaching a word costs a selection, a popup, and a typed correction. The app already computes a best match and already knows what it produced last week. What is the version where the machine asks first: "you replaced this by hand three times — teach it?"
